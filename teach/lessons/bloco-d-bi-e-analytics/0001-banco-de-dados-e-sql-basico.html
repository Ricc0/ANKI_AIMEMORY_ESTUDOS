Bloco D · BI e Analytics — Lição 1 (introdução ao bloco)

Banco de dados relacional: conceitos básicos e SQL essencial

Primeira lição do bloco de BI/Analytics. Antes de Data Warehouse e modelagem dimensional, você precisa do vocabulário básico de banco de dados relacional e da sintaxe SQL mínima para ler e escrever consultas — é a base de tudo que vem depois nesse bloco.

Siglas e termos desta lição
  • BI: Business Intelligence · inteligência de negócios: transformar dados em relatórios e painéis para decidir.
  • Banco de dados relacional: dados guardados em tabelas (linhas e colunas) que se relacionam entre si.
  • SQL: Structured Query Language · linguagem de consulta estruturada: a linguagem para pedir dados ao banco.
  • PK: Primary Key · chave primária: a coluna que identifica cada linha sem repetir (ex.: CPF).
  • FK: Foreign Key · chave estrangeira: coluna que aponta para a PK de outra tabela.
  • NULL: valor ausente ("não informado"). Não é zero nem texto vazio.
  • Normalização: organizar as tabelas para cada informação ficar guardada num lugar só, sem repetição.

Vocabulário básico

  • Tabela: uma coleção de dados organizados em linhas e colunas, sobre uma entidade (ex.: tabela Pedidos).
  • Registro (linha/tupla): uma instância única na tabela (um pedido específico).
  • Campo (coluna/atributo): uma propriedade de cada registro (data, valor, cliente).
  • Chave primária (PK): coluna (ou conjunto de colunas) que identifica unicamente cada registro.
  • Chave estrangeira (FK): coluna que referencia a chave primária de outra tabela, criando um relacionamento.
  • Esquema: a estrutura completa — quais tabelas existem, quais colunas cada uma tem, e como se relacionam.
Exemplo de esquema

Duas tabelas relacionadas:

Clientes(id_cliente PK, nome, cidade)
Pedidos(id_pedido PK, id_cliente FK, valor, data)

Pedidos.id_cliente é chave estrangeira: aponta para Clientes.id_cliente. Isso evita repetir nome e cidade do cliente em cada linha de pedido — cada dado mora em um só lugar (é a ideia de normalização).

SQL essencial: SELECT, WHERE, ORDER BY

Para deixar os exemplos concretos, considere estes dados reais nas tabelas:

Clientes 
id_cliente | nome     | cidade
-----------|----------|----------
1          | Ana      | Brasília
2          | Bruno    | Salvador
Pedidos 
id_pedido | id_cliente | valor  | data
----------|------------|--------|-----------
101       | 1          | 80,00  | 2026-07-01
102       | 1          | 250,00 | 2026-07-15
103       | 2          | 400,00 | 2026-07-20
SELECT id_pedido, valor, data
FROM Pedidos
WHERE valor > 100
ORDER BY data DESC;

Lê-se: "traga id_pedido, valor e data da tabela Pedidos, apenas onde o valor é maior que 100, ordenado da data mais recente para a mais antiga." Resultado, usando os dados acima: 

id_pedido | valor  | data
----------|--------|-----------
103       | 400,00 | 2026-07-20
102       | 250,00 | 2026-07-15

O pedido 101 (valor 80,00) fica de fora — não passa no filtro valor > 100. Os pedidos 102 e 103 passam, e aparecem ordenados da data mais recente (103) para a mais antiga (102), como pede o ORDER BY data DESC.

Funções de agregação combinadas com GROUP BY resumem dados:

SELECT id_cliente, SUM(valor) AS total_gasto, COUNT(*) AS n_pedidos
FROM Pedidos
GROUP BY id_cliente
HAVING SUM(valor) > 500;

GROUP BY agrupa as linhas por cliente antes de agregar; HAVING filtra os grupos resultantes (diferente de WHERE, que filtra linhas antes de agrupar). Com os dados acima: cliente 1 soma 80+250=330; cliente 2 soma 400. Nenhum grupo passa de 500 — o resultado é uma tabela vazia. É um detalhe fácil de esquecer: HAVING pode eliminar todas as linhas.

Exemplo resolvido — JOIN

Para trazer o nome do cliente junto com seus pedidos:

SELECT c.nome, p.valor, p.data
FROM Pedidos p
JOIN Clientes c ON p.id_cliente = c.id_cliente;

O JOIN combina as duas tabelas casando p.id_cliente (FK) com c.id_cliente (PK) — é assim que se navega entre tabelas relacionadas [1]. Resultado: 

nome  | valor  | data
------|--------|-----------
Ana   | 80,00  | 2026-07-01
Ana   | 250,00 | 2026-07-15
Bruno | 400,00 | 2026-07-20
Pegadinha clássica WHERE campo = NULL nunca retorna linhas, mesmo quando existem valores nulos na coluna — NULL não é igual a nada, nem a si mesmo, em lógica SQL padrão (é "desconhecido"). Para filtrar nulos, o correto é WHERE campo IS NULL. Bancas adoram colocar = NULL num item para testar se você sabe disso.

Pratique: certo ou errado

Item 1

A cláusula WHERE é usada para filtrar grupos após a aplicação de GROUP BY, enquanto HAVING filtra linhas individuais antes do agrupamento.

Isso marcaria como certa, mas as definições estão trocadas — veja abaixo.
Correto, o item está errado — é o inverso: WHERE filtra linhas antes de agrupar; HAVING filtra grupos depois.
Item 2

A expressão WHERE valor = NULL retorna corretamente todas as linhas em que a coluna valor está nula.

Isso marcaria como certa, mas é a pegadinha clássica acima.
Correto, o item está errado. = NULL nunca retorna linhas; o correto é IS NULL.
Item 3

Uma chave estrangeira em uma tabela referencia a chave primária de outra tabela, estabelecendo um relacionamento entre elas.

Correto — é a definição de chave estrangeira (FK).
Releia o vocabulário básico: é exatamente essa a função da FK. O item está certo.
Item 4

Considerando os dados de exemplo (3 pedidos, cliente 1 com 2 pedidos somando 330,00 e cliente 2 com 1 pedido de 400,00), a consulta com GROUP BY id_cliente HAVING SUM(valor) > 500 retorna o cliente 2 como resultado.

Isso marcaria como certa, mas nenhum grupo passa de 500 — veja abaixo.
Correto, o item está errado. Cliente 1 soma 330,00 e cliente 2 soma apenas 400,00 — nenhum ultrapassa 500, então o resultado é uma tabela vazia, sem nenhuma linha.
